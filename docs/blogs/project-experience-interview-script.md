# 项目经历面试口述稿

以下内容按口语表达整理，可根据面试时间和岗位要求选择项目展开。方括号中的提示不需要在面试中照读。

## 开场概述

我参与的项目主要集中在 GIS 智能选址、企业内部知识库、通用业务平台和工程构建优化几个方向。工作内容既包括 React 前端和地图可视化，也涉及 Spring Boot、NestJS、PostgreSQL/PostGIS、Redis 等后端和数据能力。在项目中，我做过开发负责人，也独立主导过平台和系统的设计落地。

如果重点介绍 GIS 方向，我会以霸王茶姬的智能选址系统为例；如果重点介绍平台能力，可以展开选址服务基础平台或集团主数据接入平台；如果重点关注工程效率，则可以介绍大型 MPA 项目的构建优化。

## 1. 霸王茶姬 GIS 智能选址系统

霸王茶姬拓店选址之前比较依赖经验判断，缺少把区域 AOI、POI、客流和商业热力等数据整合起来的决策工具。公司本身已经有成熟的产品平台，所以这个项目不是从零搭一套系统，而是在现有平台上扩展面向这条业务线的 GIS 选址模块。

我在项目中担任开发负责人，主要负责架构设计和核心功能落地。前端使用 React 和 Leaflet 实现动态地图渲染，后端使用 Spring Boot，并通过 PostgreSQL 和 PostGIS 接入业务数据。数据方面，我们对接并清洗高德的 POI 围栏、AOI 面状数据、实时客流和商业热力数据，再结合 Grid 格网切片，通过热力图和聚合图展示客流及经济指标。

针对海量坐标的几何查询，我们在 PostGIS 中增量构建 GiST 空间索引，优化查询效率。最终，这个模块服务于核心业务线的拓店决策，帮助业务从主要依靠经验判断，逐步转向数据驱动。

## 2. 企业内部知识库与聊天机器人

这个项目主要是为了解决公司产品框架文档缺失、模块说明难以落地的问题。当时新员工和跨部门同事了解产品架构比较慢，很多问题需要重复沟通。

我独立设计并搭建了企业级 RAG 问答系统，支持 Markdown、Swagger 和 Wiki 等内容检索。整体链路包括 React、NestJS、LangChain 和 Qdrant，前端基于 Dify 编排。针对不同来源的文档，我设计了异构文档 ETL 流程，并使用 LangChain 做文档切片和 Embedding 向量化；检索侧使用 Qdrant 和余弦相似度，提升文档及 API 内容的召回精准度。

对话体验方面，我基于 NestJS 和 SSE 实现了连续对话，设计了对话历史存储，并用 LLM 自动摘要对话。系统上线后获得了团队的正向反馈，减少了因文档缺失带来的重复沟通，也成为新同事了解产品架构的辅助工具。

## 3. 选址服务基础平台

GIS 选址、门店拓展等上层业务都会用到缓存、权限、动态查询和表单等通用能力。如果每个业务都重复建设，稳定性和扩展性都会受到影响。因此，我独立主导设计了一套通用技术底座，为上层选址业务提供支撑。

缓存方面，我设计了接口化缓存组件并统一 Redis 序列化规范，同时通过随机 TTL 降低缓存雪崩风险，通过空值缓存防止缓存穿透。动态查询方面，我基于 SpEL 设计变量解析器，让配置端可以灵活定义规则。

权限和元数据方面，我设计了级联字典表和全局配置服务，重构菜单管理，使动态配置可以实时生效，并实现页面、按钮、接口三级 RBAC，结合路由过滤和 JWT 控制访问。动态表单则采用“主表加字段配置表”的方案，用 PostgreSQL JSONB 存储异构数据。

这套平台为霸王茶姬 GIS 选址系统提供了缓存、权限和动态查询等底层能力。菜单权限可以动态配置，表单调整也不需要做 DDL 变更，从而降低了运维和迭代成本。

## 4. 大型 MPA 项目构建性能优化

公司当时的大型 MPA 项目存在构建速度慢、产物体积臃肿的问题。我独立主导了构建工具链升级，目标是同时改善构建速度和生产产物体积。

工具链上，我把原有方案切换到 Rspack 和 SWC，并采用 sass-embedded 和 SwcJsMinimizer。依赖治理方面，我修正了 dependencies 和 devDependencies 归属混乱的问题，减少生产依赖体积和相关安全风险。

分包方面，我重新设计 splitChunks 策略，用 minChunks 设置公共包准入门槛，再通过 cacheGroups 和 priority 分层调优 React、jQuery 等依赖，并把登录页和重型库隔离。为了便于分析构建结果，我还引入 Rsdoctor 和 BundleAnalyzer 来可视化依赖拓扑、定位冗余依赖。

优化之后，生产构建速度提升了 5 倍以上，全站首屏 JS 体积削减约 40%，改善了研发效率和首屏体验。

## 5. 集团主数据接入平台

集团上游系统会下发用户、角色、区划、职位、菜单、部门和权限等主数据，但数据源异构，原来的消费链路扩展性不足；分布式 MQ 的联调和排查也比较困难，同时认证体系需要升级。

我负责重构主数据消费链路，让异构数据源能够插拔式接入，并落地 JWT 双 Token 和 OAuth 互信体系。架构上使用策略模式和工厂模式，把数据解析、清洗和分发解耦。日志方面，基于 Spring AOP 统一收口，并将 MQ 消费日志与系统运行日志非侵入式地分离。

为方便调试，我设计了 Controller 模拟测试接口，形成从请求、模拟下发到消费验证的闭环沙箱。认证方面，落地 AccessToken 和 RefreshToken 双 Token，用 Redis 管理 RefreshToken 生命周期，支持无感刷新和动态销毁；同时提供 OAuth 接口支持三方 Token 互换。

改造后，新业务接入成本降低，分布式场景下的排查和联调效率也有明显提升；在提供无感刷新的同时，认证体系也得到了加强。

## 6. 赛百味 GIS 智能选址模块

赛百味全国门店拓店需要采集候选点位、评估周边商圈，并把选址信息衔接到审批流程。我作为开发者，基于现有 GIS 平台定制开发了独立的“机会点”采集和分析模块。

前端使用 React 开发机会点标注页面，并将它作为独立模块嵌入平台，与主系统解耦。数据方面，对接腾讯位置大数据，按照步行和骑行两种商圈口径获取并展示人口、金融和客流数据。机会点及周边数据通过 HTTP 接口推送到第三方流程系统，打通采集、补充和审批流程。

此外，我基于飞书 OAuth 网页授权实现免登录进入，并用 Java 异步多线程开发批量取数工具，可以并发获取多个点位的周边数据。这个模块支持全国范围选址，批量取数替代了人工逐点查询，也通过免登录降低了业务人员的使用门槛。

## 7. 茶百道 GIS 选址模块

茶百道需要查看多层级经营数据，并为门店拓展提供数据依据。我作为开发者，在现有 GIS 平台上定制开发了经营看板和机会点选址两个模块。

经营看板支持全国、省、市、区四级下钻，用户可以在地图上逐级切换行政区，并联动查看相关指标。我还开发了单店维度的看板，展示经济指标和业绩完成度，支持从区域视图进一步查看门店情况。

机会点选址方面，我开发了机会点采集页面，对接腾讯位置大数据和热力接口，将周边人口、客流和热力数据可视化。最终，业务人员可以从宏观区域逐步查看到单店经营情况，为拓店决策提供数据依据。
