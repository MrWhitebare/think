# 面试问题记录

## 第一个问题：MySQL 和 PostgreSQL 的区别

### 一、存储引擎架构（最本质的区别）

**MySQL (InnoDB)**：**聚簇索引**架构 —— 主键索引本身就是数据存储的地方，数据按主键顺序物理存放。二级索引存的是"索引列 + 主键值"，回表时用主键值再查一次主键索引。

**PostgreSQL**：**堆表（Heap）**架构 —— 数据不按任何顺序存储，所有索引（包括主键）都是独立结构，存的是"索引列 + 物理行地址（TID）"。回表是拿 TID 直接定位堆表的物理位置。

（这个我们之前已经聊过，你的 GiST 索引场景就属于 PostgreSQL 的索引体系）

### 二、MVCC（多版本并发控制）实现方式不同

**MySQL (InnoDB)**：通过 **Undo Log** 实现——旧版本数据存在 Undo Log 里，需要历史版本时去 Undo Log 里"倒推"出来。更新操作是**原地更新**（in-place update），空间利用率相对较高。

**PostgreSQL**：**每次更新都会生成一个新的行版本**（更新 = 插入新行 + 标记旧行失效），旧版本数据直接留在表里，不是删除。所以 PostgreSQL 需要定期 **VACUUM** 清理这些失效的旧版本，否则表会不断膨胀（这也是为什么之前提到 Index-Only Scan 依赖 VACUUM 更新 Visibility Map）。

### 三、功能特性对比

| 维度 | MySQL | PostgreSQL |
| --- | --- | --- |
| JSON | 支持 JSON 类型，功能较基础 | **JSONB**，支持索引（GIN）、更强的查询能力，你的动态表单项目正是用了这个 |
| 空间数据 | 空间数据支持较弱，需要额外配置 | **PostGIS 扩展**功能强大，是空间数据处理的行业标准（你的 GIS 选址项目用的正是这个） |
| 全文检索 | 基础支持 | 更强大的原生全文检索 |
| 窗口函数 / CTE | 较晚支持，功能较弱 | 支持完善，SQL 标准兼容度更高 |
| 扩展性 | 相对固定 | **插件化架构**，可以装 PostGIS、pg_trgm 等扩展 |
| 并发写入性能 | 并发写入场景通常表现更好 | 复杂查询、分析型场景表现更好 |

### 四、适用场景

- **MySQL**：互联网高并发、读写量大的业务系统（电商订单、用户系统），生态成熟、运维经验丰富、社区资料多
- **PostgreSQL**：需要复杂查询、GIS 空间数据、JSON 灵活存储、数据分析场景——**这也是为什么你的项目会选 PostgreSQL**（GIS 选址需要 PostGIS，动态表单需要 JSONB）

### 五、总结

如果面试官问“MySQL 和 PostgreSQL 的区别”，我会直接强调两点：

1. **MySQL 更适合高并发业务系统**，尤其是传统 Web 场景。
2. **PostgreSQL 更适合复杂查询、空间数据、JSON/分析型场景**，也更符合你之前项目中真实的用法。

所以，答案不应该只停留在“哪个更好”，而是要说清楚：

> MySQL 和 PostgreSQL 的差异，本质上是它们在数据组织方式、并发控制、功能能力上的设计取舍不同；而你最终选择哪个，取决于业务场景。

### 口播版

> MySQL 更适合高并发的业务系统，PostgreSQL 更适合复杂查询、GIS、JSON 这类扩展能力更强的场景。简单说，MySQL 更偏业务型高并发，PostgreSQL 更偏复杂分析和扩展能力。

## 第二个问题：Spring Boot 中事务分为哪两种？

Spring Boot 里常见的事务大致可以分成两类：

### 一、声明式事务

这是最常用、最推荐的方式。核心就是在方法或类上加 `@Transactional`。Spring 会通过 AOP 代理在方法执行前开启事务，方法执行结束后根据结果提交或回滚。

它的优点是：

- 代码侵入少
- 事务逻辑和业务逻辑分离
- 适合大多数服务类场景

### 二、编程式事务

这是手动控制事务的方式，通常用：

- `TransactionTemplate`
- `PlatformTransactionManager`
- `TransactionStatus`

这种方式更灵活，比如你想在某些复杂逻辑里精确控制事务边界、提交时机、异常处理时，就会用编程式事务。

### 核心原理：事务是绑定在"线程"上的，不是绑定在"方法"上的

Spring 声明式事务的底层实现，本质上是**把数据库连接（Connection）绑定到当前线程的 ThreadLocal 里**。

具体流程：

1. A 方法被调用时，Spring AOP 的代理拦截到 `@Transactional` 注解，**开启事务、获取一个数据库连接，把这个连接绑定到当前线程的 ThreadLocal**
2. A 方法内部调用 B（不管是同一个类里直接调用 `this.b()`，还是调用另一个 Bean 的方法），**只要还在同一个线程里执行**
3. B 方法里如果有数据库操作（比如 `mapper.update()`），Spring 会先去 ThreadLocal 里**检查当前线程有没有已经绑定的连接**——发现有（就是 A 开启的那个连接），**直接复用这个连接**，而不是重新开一个
4. 所以 B 的数据库操作，实际上用的是和 A 同一个连接、同一个事务——**B 并不知道自己"在事务里"，只是恰好用了和 A 相同的连接**

**这就是为什么 B 没加 `@Transactional`，效果上却像是"生效了"** —— 不是事务传递给了 B，而是**它们共用了同一个线程绑定的数据库连接**。

### A 函数加了声明式事务，B 函数没有，事务对 B 是否也生效？

可以这么理解：

- **B 不会自己单独开启一条新的事务**。
- 但如果 `A` 已经在事务中，`B` 在同一调用链里执行，那么 `B` 的数据库操作会**默认参与到 A 的事务上下文中**。

也就是说：

- `B` 没有 `@Transactional`，不代表它完全脱离事务。
- 只要它在 `A` 的事务范围内执行，`B` 的写库操作仍然会受 `A` 的事务控制。

这就是事务的**传播性**：

- `@Transactional` 的默认传播行为是 `REQUIRED`
- 也就是说：如果当前线程已经有事务，就加入现有事务；如果没有，就新开启一个事务

所以在大多数情况下，答案是：

> 对，`B` 的数据库操作会受到 `A` 事务的影响；但它不是自己单独开启事务，而是“加入”了 `A` 的事务。

### 什么情况下会失效（B 不会被纳入 A 的事务）

1. **B 是异步调用**（比如加了 `@Async`，或者手动开了新线程执行）—— 新线程有自己独立的 ThreadLocal，拿不到 A 绑定的连接，B 会用一个全新的连接，完全不在 A 的事务里
2. **B 自己声明了 `@Transactional(propagation = Propagation.REQUIRES_NEW)`** —— 这个传播行为会强制挂起当前事务、开一个全新的事务，B 用的是新连接，和 A 的事务完全独立
3. B 操作的是**不同的数据源（DataSource）** —— 比如 A 操作数据库 1，B 操作数据库 2，两个连接池不同，自然不可能共用一个连接

### 真正的原因：不是因为"同一个线程"，而是"异常向上传播，被 A 的事务拦截器捕获"

"同一个线程"这个前提，只是解释了**为什么 A 和 B 共用同一个数据库连接**（我们上一条讲的内容），但**回滚这个动作，靠的是另一个机制——异常的方法调用栈传播**。

具体过程是这样的：

1. A 方法被 Spring AOP **代理**包裹（这是 `@Transactional` 生效的关键——本质是一个动态代理对象在 A 方法**外面**包了一层"事务拦截逻辑"）
2. 代理逻辑大概是：

```java
开启事务
try {
    调用真正的 A() 方法体   // A 内部又调用了 B()
    提交事务
} catch (Exception e) {
    回滚事务
    抛出异常
}
```

3. B 方法执行时抛出异常 → 这个异常**不会被 B 自己处理**（因为 B 没有事务逻辑，也没有 try-catch 吞掉它）→ 异常**沿着 Java 方法调用栈，一层层往上抛**，从 B 抛回到 A 方法体内
4. 因为 A 方法体是被**代理的 try-catch 包裹**的，这个异常最终**被 A 外层的事务拦截器捕获**到，拦截器一看"有异常"，就执行**回滚**

**所以本质是**：B 抛出的异常，通过**正常的 Java 异常传播机制**（一层层网上冒泡），最终被**A 的事务代理捕获**，回滚的决策是**A 的代理逻辑做的**，跟"是否同一个线程"没有直接关系——"同一个线程"只是保证了 A 和 B 用的是同一个连接，这样"回滚"这个动作对 B 做的数据库操作也能生效（因为回滚的是这个连接上的所有未提交操作）。

### 一个重要的坑：如果 B 自己 try-catch 吞掉了异常呢？

**这是一个高频追问**——如果 B 内部自己捕获了异常，没有再往外抛：

```java
public void b() {
    try {
        mapper.update(...);
        throw new RuntimeException("出错了");
    } catch (Exception e) {
        log.error("B出错了", e);
        // 异常被吞掉了，没有再往外抛
    }
}
```

**这种情况下，A 的事务不会回滚**——因为异常根本没有传播到 A 那里，A 的事务代理压根不知道出过异常，会正常走到`提交事务`那一步。这是实际开发中**最常见的事务失效场景之一**：业务代码里加了 try-catch 但没有重新抛出异常（或者没有手动调用 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`），导致事务"看起来加了，其实没生效"。

---

**再追问一个**：如果 B 抛出的是一个**受检异常（Checked Exception，比如自定义的 `Exception` 而不是 `RuntimeException`）**，A 的事务还会回滚吗？为什么？

这个是 Spring 事务里一个经典的坑，很多人踩过，讲清楚。

### 答案：不会回滚（除非额外配置）

**Spring 声明式事务默认的回滚规则是**：**只对 `RuntimeException`（运行时异常）和 `Error` 回滚，对受检异常（Checked Exception）不回滚**。

这是 Spring 的**默认行为**，源自一个历史设计理念——Spring 认为：

- **RuntimeException（非受检异常）**通常代表"意料之外的系统性错误"（比如空指针、数据库连接失败），应该回滚
- **Checked Exception（受检异常，比如自定义的 `Exception` 子类）**通常代表"业务上可以预期、需要调用方处理的情况"（比如"库存不足异常"、"余额不足异常"），Spring 认为这种异常"不一定是失败"，所以默认不回滚

### 举个例子说明这个坑

```java
@Transactional
public void a() throws MyBusinessException {
    mapper.insert(order);
    b(); // b 抛出一个受检异常
}

public void b() throws MyBusinessException {
    if (库存不足) {
        throw new MyBusinessException("库存不足"); // 继承自 Exception，不是 RuntimeException
    }
}
```

**这种情况下，即使异常正常抛到了 A、事务代理也捕获到了这个异常，事务依然不会回滚**——因为 Spring 一看这是个受检异常，默认判断"这个不用回滚"，`mapper.insert(order)` 这行操作会被**正常提交**，造成脏数据（订单插入了，但库存检查失败了）。

### 怎么解决（这是必须记住的知识点）

**方式一：显式指定要回滚的异常类型**

```java
@Transactional(rollbackFor = Exception.class)
public void a() throws MyBusinessException {
    ...
}
```

`rollbackFor = Exception.class` 明确告诉 Spring："只要抛出 Exception（包括所有受检异常），都要回滚"。**这也是为什么实际项目里，几乎所有团队的编码规范都要求 `@Transactional` 必须加上 `rollbackFor = Exception.class`**，不能只写裸的 `@Transactional`——不然一旦代码里抛的是受检异常，事务就悄悄失效了，这是生产环境中一个非常隐蔽、容易被面试官考察的"事务失效场景"。

**方式二：手动标记回滚**

```java
try {
    ...
} catch (MyBusinessException e) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    throw e;
}
```

---

**这里给你梳理一下"Spring 事务失效的常见场景"，这是一个非常高频的八股文考点，建议你直接背下来这几条**：

1. 方法内部自调用（`this.b()`）——因为没走代理，AOP 不生效
2. 方法权限不是 `public`（Spring AOP 默认只代理 public 方法）
3. 异常被自己 try-catch 吞掉，没有重新抛出
4. 抛出的是受检异常，但没有配置 `rollbackFor`
5. 数据库引擎不支持事务（比如 MySQL 用了 MyISAM 而不是 InnoDB）
6. 多线程/异步场景，事务不会跨线程传播

### 口播版

> Spring Boot 的事务主要分成声明式事务和编程式事务两种。声明式事务最常见，就是在方法上加 @Transactional；编程式事务就是手动控制事务边界。关键要记住的是，事务绑定的是当前线程的数据库连接，所以同一线程里调用会复用同一事务，而异步、REQUIRES_NEW 或不同数据源都会导致事务隔离。

## 第三个问题：@Component 和 @Service 的区别

本质上没区别，它们的注解定义上都标注了 `@Component`，属于 Component 的派生注解，Spring 扫描组件时都会识别并注册成 Bean。

区分它们主要是为了语义化，标明这个类在架构里属于哪一层（表现层 / 业务层 / 数据层），提高代码可读性。

**唯一有实际功能区别的是 `@Repository`**，Spring 会对它做异常转换，把底层持久层框架抛出的各种异常统一转换成 `DataAccessException` 体系，这是其他几个注解没有的特性。

### 如果面试官继续追问：我能不能自己定义一个 `@MyComponent` 注解？

答案是**可以**，这正是 Spring 允许自定义 stereotype annotation 的设计，一些团队会自定义比如 `@Manager`、`@Facade` 这种更贴合自己项目分层架构的注解。

### 那为什么还要分这么多个？—— 语义化 + 分层架构

这几个注解存在的意义，是为了**在代码层面标明这个类属于架构的哪一层**，让代码可读性更好、职责更清晰：

- `@Controller`：表示层 / 控制层，处理 HTTP 请求
- `@Service`：业务逻辑层，处理业务逻辑
- `@Repository`：数据访问层，操作数据库
- `@Component`：通用组件，不属于上面三层的其他 Bean（比如工具类、配置类）

这属于 Spring 提倡的**"约定优于配置"**思想——你一看到 `@Repository`，不用看代码内容就知道这是操作数据库的类。

### 一个容易忽略的加分点：`@Repository` 有一个额外功能

这是一个**容易被忽略的加分点**——`@Repository` 除了标记语义，还有一个**实际功能上的区别**：Spring 会对标了 `@Repository` 的类做**异常转换（Exception Translation）**。

具体来说：不同的持久层框架（JDBC、Hibernate、JPA 等）会抛出各自特定的异常（比如 `SQLException`、`HibernateException`），这些异常五花八门、不统一。Spring 通过 `@Repository` 注解，配合 `PersistenceExceptionTranslationPostProcessor`，会自动把这些**框架相关的异常**转换成 Spring 统一的 `DataAccessException` 体系下的异常，让上层代码不需要关心底层用的是哪个持久层框架，捕获异常时更加统一。

**这是 `@Repository` 唯一比 `@Component` / `@Service` 多出来的实际功能，其他几个注解都没有这个特性。**

### 口播版

> @Component 和 @Service 本质上都属于 Spring 的组件扫描范围，区别主要在语义上。@Service 表示业务层，@Repository 多了一个异常转换的功能，所以在面试里可以重点提这个点。

## 第四个问题：什么是回表

在使用**非聚簇索引（二级索引）**查询时，索引里只存储了索引列的值和主键值，**并不包含这一行的完整数据**。如果查询的字段不在这个二级索引里，数据库就需要**拿着索引查到的主键值，再回到主表（聚簇索引 / 数据本体）里查一次完整数据**——这个过程就叫"回表"。

### 例子说明

比如有一张表：

```text
id | name | age | address
```

如果你执行：

```sql
SELECT name, age FROM t WHERE age = 18;
```

那么二级索引可能存的是：

```text
(age) -> (主键 id)
```

索引里并没有完整的 `name` 和 `address` 字段。数据库先通过 `age = 18` 找到对应的 `id`，再根据这个 `id` 去主表里取整行数据，这个过程就是回表。

### 回表的本质

回表的核心意思就是：

- **索引查到了目标记录的定位信息**
- 但**索引本身不保存整行数据**
- 所以还要再去主表拿完整数据

### 为什么会影响性能

因为回表会带来额外的随机 I/O 和额外的查表开销，所以在数据库优化里，回表通常被认为是一种性能代价。

### 如何减少回表

常见的优化思路有：

1. **覆盖索引**：把查询需要的字段都放进索引里，避免回表
2. **索引设计更合理**：让查询条件和返回字段尽量覆盖在同一个索引里
3. **避免过度使用二级索引**：如果查询经常需要全字段数据，可能需要评估是否该建立更合适的索引组合

### 一句话总结

> 回表，就是在使用二级索引查询时，数据库先通过索引定位到主键，再回到主表取完整数据的过程。

### 口播版

> 回表的本质就是二级索引没有覆盖查询所需的全部字段，所以还要再回主表拿完整数据。它会带来额外的随机 I/O，因此常见的优化方式是覆盖索引、合理设计联合索引，以及减少不必要的字段查询。

### 如何处理回表问题

面试里如果被问到“怎么处理回表问题”，我会直接说：

1. **尽量使用覆盖索引**

    覆盖索引就是把查询真正需要的字段都放进索引里，避免再回到主表取完整数据。

    例如原来查询：

    ```sql
    SELECT name, age FROM t WHERE age = 18;
    ```

    如果建立了索引：

    ```sql
    CREATE INDEX idx_age_name ON t(age, name);
    ```

    那么数据库就可以直接从索引拿到 `age` 和 `name`，不需要再回表。

2. **让查询条件和返回字段尽量落在同一个索引里**

    这是索引设计的核心思路。索引最有价值的地方，不只是能快速定位记录，还在于它能尽量覆盖本次查询。所谓“有用的索引”，往往不是单独看是否命中，而是看它能不能减少回表。

3. **减少不必要的字段查询**

    如果查询语句本身就返回了大字段，比如 `text`、`blob`、超长字段，那么即使能走索引，也可能因为字段过大导致回表成本更高。所以在查询设计时，尽量只查真正需要的字段。

4. **联合索引的顺序很关键**

    联合索引设计时，最先放最常用且选择性高的列。否则即使建立了索引，很多场景也可能因为字段顺序不合理，导致索引无法高效命中。

5. **在业务允许的情况下，考虑反范式设计**

    如果某些查询频繁并且需要大量字段组合，适当的冗余字段设计，也能减少回表带来的性能损耗。

### 面试里常见的答法

如果面试官继续追问，我会这样回答：

> 回表问题本质上是“二级索引不能覆盖完整查询结果”的问题。最常见的处理方式就是覆盖索引、合理设计联合索引、减少不必要查询字段，以及在特定场景下做反范式优化。

### 一点补充：覆盖索引不是万能的

覆盖索引确实能显著减少回表，但它也有代价：

- 索引会变大
- 索引维护成本会增加
- 不是所有查询都适合把大量字段放进索引里

所以真正的优化思路，不是“索引越大越好”，而是**根据查询模式，做针对性的索引设计**。

## 第五个问题：如何设计一个表的索引

### 一、语法层面：怎么加索引

```sql
-- 1. 建表时直接定义索引
CREATE TABLE user (
    id INT PRIMARY KEY,        -- 主键索引，自动创建
    name VARCHAR(50),
    age INT,
    email VARCHAR(100),
    INDEX idx_name (name),                 -- 单列索引
    INDEX idx_name_age (name, age),        -- 联合索引（复合索引）
    UNIQUE INDEX idx_email (email)         -- 唯一索引
);

-- 2. 给已有的表添加索引
CREATE INDEX idx_name ON user(name);
ALTER TABLE user ADD INDEX idx_name (name);

-- 3. PostgreSQL 里加空间索引（结合你的 GIS 项目）
CREATE INDEX idx_geom ON poi_table USING GIST (geom);

-- 4. 删除索引
DROP INDEX idx_name ON user;          -- MySQL
DROP INDEX idx_name;                  -- PostgreSQL
```

### 二、设计层面：怎么判断一个字段该不该建索引

这个才是面试真正想考察的部分——**不是问你语法，是问你的判断逻辑**。

#### 应该建索引的情况

1. **经常出现在 `WHERE` 条件里的字段**

```sql
SELECT * FROM order WHERE user_id = 123;  -- user_id 应该建索引
```

2. **经常用于 `JOIN` 关联的字段**（外键字段）

```sql
SELECT * FROM order o JOIN user u ON o.user_id = u.id;  -- order.user_id 应该建索引
```

3. **经常用于 `ORDER BY` / `GROUP BY` 的字段**

    索引本身是有序的，可以避免额外的排序操作。

4. **区分度高（选择性好）的字段**

    比如 `user_id`、`email` 这种值很分散的字段，索引效果好；而像“性别”这种只有男/女两个值的字段，建索引意义不大（因为一次查询可能命中一半的数据，索引反而不如全表扫描快）。

### 三、索引设计的核心原则

#### 1. 优先建“查询最频繁”的字段

如果一个字段永远不在查询条件里，或者很少被访问，那建索引的意义就很有限。

#### 2. 选择性好的字段比“有大量重复值”的字段更适合建索引

例如：

- `user_id`、`email`：选择性高，适合建索引
- `gender`、`status`：重复值多，索引收益可能较低

#### 3. 索引不是越多越好

索引越多，写入性能可能越差，维护成本越高。尤其是频繁写入的表，盲目加索引会拖慢插入、更新、删除。

#### 4. 联合索引比单列索引更常见

很多真实业务场景，都是“多个字段一起筛选”。这种情况下，联合索引往往比单列索引更有价值。

### 四、联合索引的设计方法

联合索引的顺序非常重要，通常遵循以下原则：

1. **把选择性高、过滤能力强的字段放前面**
2. **把最常出现在 `WHERE` 条件里的字段放前面**
3. **把等值查询字段放前面，范围查询字段放后面**

例如：

```sql
CREATE INDEX idx_user_status_time ON order(user_id, status, create_time);
```

在这种索引里：

- 先按 `user_id` 精确定位
- 再按 `status` 过滤
- 最后按 `create_time` 做范围筛选

这个索引往往会比单独索引更高效。

### 五、常见误区

#### 1. 只看“字段是不是经常查询”，不看“查询结果是否需要回表”

如果查询返回大量字段，而索引里没有这些字段，最终还是会回表。这个时候，光有索引不够，可能还要考虑覆盖索引。

#### 2. 看到“字段很长”，就默认不建索引

字段长度本身不是决定因素，真正重要的是：

- 查询频率
- 选择性
- 是否能覆盖查询
- 是否会带来写入开销

#### 3. 把所有字段都建索引

这是非常常见的错误。数据库不是“索引越多越快”，而是“有针对性的索引更有用”。

### 六、一个更实际的面试回答

如果面试官问“你会如何设计一个表的索引”，我会这样回答：

> 首先看这个表的查询模式：哪些字段经常出现在 `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY` 里；其次看这些字段的选择性，优先建选择性高、过滤能力强的字段；再看是否需要联合索引；最后还要评估写入成本，避免盲目加索引。简单来说，索引设计的核心就是“让常用查询尽量命中索引，并尽量减少回表”。

### 七、总结

设计索引的核心，不是背语法，而是判断：

- 哪些字段值得索引
- 索引应该怎么组合
- 查询能不能被索引覆盖
- 写入成本是否可接受

一句话概括：

> 索引设计的本质，是在“查询性能”和“写入成本”之间做平衡，并让最常用的查询尽量走索引、尽量少回表。

### 口播版

> 建索引的关键不是背语法，而是看查询模式。先看哪些字段常出现在 WHERE、JOIN、ORDER BY 里，再看选择性和写入成本，最后用联合索引尽量让常用查询命中，并减少回表。

## 第七个问题：最左前缀匹配是什么

**最左前缀匹配原则**是联合索引（复合索引）的一个核心使用规则：**联合索引在查询时，必须按照建索引时字段的顺序，从最左边的字段开始连续使用，索引才能生效；一旦中间跳过某个字段，后面的字段就用不上索引了。**

### 举例说明

假设建了这样一个联合索引：

```sql
CREATE INDEX idx_a_b_c ON table1(a, b, c);
```

这个索引在底层的存储结构（B+ 树）中，是**先按 a 排序，a 相同的情况下再按 b 排序，b 也相同的情况下再按 c 排序**——类似字典排序的逻辑（先比第一个字，第一个字一样再比第二个字）。

#### 能用上索引的情况

```sql
WHERE a = 1                          -- ✅ 用到 a，索引生效
WHERE a = 1 AND b = 2                -- ✅ 用到 a、b，索引生效
WHERE a = 1 AND b = 2 AND c = 3      -- ✅ 全部用到，索引完全生效
WHERE a = 1 AND c = 3                -- ✅ 但只有 a 部分用上索引，c 这个条件用不上索引（因为跳过了 b）
```

#### 用不上索引的情况

```sql
WHERE b = 2                          -- ❌ 索引完全用不上，因为没有从最左边的 a 开始
WHERE c = 3                          -- ❌ 同上，完全用不上
WHERE b = 2 AND c = 3                -- ❌ 跳过了 a，索引用不上
```

### 为什么会有这个限制——用字典类比理解

想象一本字典，是按照"姓氏首字母"排序的。如果你想查"姓王的人"，可以直接翻到"王"字母那一页——这就相当于用了最左边的索引字段。

但如果你想查"名字第二个字是'伟'的人"（不管姓什么），字典帮不上忙，因为字典是按姓氏排的，"名字第二个字"这个信息在字典里是**杂乱无序分布**的，你只能一页一页翻完整本字典——这就是"跳过最左字段，索引失效"的原因：**联合索引的有序性，是从左往右逐层建立的，一旦左边的字段条件不确定（没有指定或者用了范围查询），右边字段在索引里的物理位置就变得杂乱无章，没法利用索引的有序性去快速定位。**

### 一个容易搞混的细节：范围查询会"断开"最左前缀

```sql
WHERE a = 1 AND b > 2 AND c = 3
```

- `a = 1`：用上索引 ✅
- `b > 2`：用上索引 ✅（范围查询也能用索引，只是范围内的结果不再是精确定位）
- `c = 3`：**用不上索引** ❌——因为 `b` 是范围查询而不是精确等值，`b>2` 范围内对应的记录，`c` 字段的值在索引里已经不是连续有序排列的了，所以 c 这个条件没法再借助索引快速判断，只能等回表后在 Server 层过滤

**这也是为什么我们之前讲索引下推时提到 "a 等值、b 范围、c 等值" 这种场景，c 字段能不能下推不确定——根源就在这里：范围查询会打断最左前缀链条上后续字段的有序性。**

### 设计索引时的实践指导

正因为这个规则，**设计联合索引字段顺序时的原则是：**

- 把**最常用作精确查询条件（等值查询）**的字段放在最左边
- 把**范围查询的字段尽量放在最后面**，避免它把后面本可以利用索引的字段"打断"

比如你有 `WHERE user_id = ? AND create_time > ? AND status = ?` 这种查询，索引应该建成 `(user_id, status, create_time)`，把两个等值条件（`user_id`、`status`）放前面，范围条件（`create_time`）放最后，这样能让所有字段尽可能都用上索引。

---

**一句话总结**：**最左前缀匹配 = 联合索引必须从最左边的字段开始、按顺序连续使用，中间不能跳字段；遇到范围查询会打断后面字段的索引有效性。** 这个规则直接决定了你设计联合索引时，字段应该按什么顺序排列。

### 口播版

> 最左前缀匹配就是说，联合索引必须从最左边字段开始按顺序使用，不能跳过中间列。它的核心思想是，联合索引本质上是按字段顺序有序存储的，所以设计时要把等值条件放前面，范围条件尽量放后面。

## 第六个问题：索引下推是什么

### 核心定义

**索引下推（Index Condition Pushdown）**：MySQL 5.6+ 引入的优化机制，把原本需要"回表后"才能做的过滤条件，提前放到**索引扫描阶段**就完成判断，从而减少不必要的回表次数。

### 生效的前提条件

1. 必须是**联合索引**（单列索引没有下推的意义）
2. **索引前面的字段是范围/模糊查询**（如 `LIKE '张%'`、`>`、`<`），导致索引无法精确定位、产生一批候选记录
3. **索引后面还有其他字段的过滤条件**，且这个条件能在索引里直接判断（简单等值/范围比较，不涉及复杂函数计算）

### 关键纠正点：不是"只要满足最左前缀就会触发"

场景举例是否需要"下推"

- 全部等值匹配 `WHERE a=1 AND b=2` ❌ 不需要，索引直接精确命中，没有多余候选记录需要过滤
- 前面范围 + 后面等值 `WHERE name LIKE '张%' AND age=20` ✅ 典型下推场景，先在索引层筛掉不满足 age 的候选，减少回表
- 中间断开最左前缀 `WHERE a=1 AND b>2 AND c=3` c 字段的索引下推能否生效不确定，取决于优化器判断

**一句话记住**：索引下推解决的是**"范围查询导致索引无法精确定位、产生多余候选记录"**这个问题，不是"只要按最左前缀写语法就自动触发"。

### 口播版

> 索引下推的核心是把原本在回表后才做的过滤条件，提前到索引扫描阶段做。它通常发生在联合索引前面有范围查询、后面还有等值过滤的场景里，目的是减少不必要的回表。

## 第八个问题：微服务相关问题

### 第1题：服务注册发现原理

服务注册发现的核心是两步：注册和发现。

- 注册：服务启动时，会把自己的服务名、IP、端口等信息主动上报给 Nacos，Nacos 会维护一个“服务名 → 实例列表”的映射。
- 发现：调用方在发起请求前，先向 Nacos 查询目标服务的健康实例列表，拿到真实的地址后，再发起调用。
- 心跳：服务注册后会周期性向 Nacos 发送心跳，告诉它自己还活着。Nacos 会根据心跳判断实例是否健康，并在实例失效时剔除它。

### 第2题：为什么 Nacos 会选错网卡

因为 Nacos 客户端在没有显式指定 IP 时，会自动探测本机 IP；在多网卡环境下，Java 的自动探测逻辑可能拿到虚拟网卡地址，所以注册时会出现选错网卡的情况。生产环境通常会显式配置注册 IP，比如 `ip: 127.0.0.1`，避免依赖自动探测。

### 第3题：FeignClient 接口没有实现类，为什么能直接注入使用

因为 Spring 启动时会扫描所有 `@FeignClient` 接口，并由 Feign 在运行时生成一个动态代理对象，把它注册为 Spring Bean。你注入的 `UserServiceClient` 实际上不是手写实现类，而是 Feign 生成的代理对象。调用方法时，代理会根据 `@GetMapping`、`@PostMapping` 等注解，把方法转换成 HTTP 请求，并把响应 JSON 反序列化成 Java 对象返回。

### 第4题：Feign 调用地址解析过程

完整链路是：

1. Feign 根据服务名 `user-service` 知道要调用哪个服务。
2. LoadBalancer 先从 Nacos 查询该服务的健康实例列表。
3. LoadBalancer 按负载均衡算法（默认轮询）从实例列表里选出一个实例。
4. Feign 用这个真实地址发起 HTTP 请求。

如果没有 `spring-cloud-starter-loadbalancer` 依赖，LoadBalancer 这一步就会失效，最终表现为请求无法正常转发或返回 503。

### 面试中可以直接这样回答

> 服务启动时会先向 Nacos 注册自己的实例信息；调用方请求时，Feign 根据服务名向 Nacos 查询健康实例列表，再由 LoadBalancer 选择某一个实例；Nacos 依赖心跳机制维护实例健康状态；如果实例失效，会被标记为不健康并从列表中剔除。Feign 通过动态代理把接口方法转换成 HTTP 调用，而不是通过手写实现类。

### 口播版

> 这题我会直接说：服务启动时会向 Nacos 注册自己的实例信息，调用时先查 Nacos 的健康实例列表，再由 LoadBalancer 选一个实例发请求；Nacos 依赖心跳机制维护实例状态。Feign 层本质上是动态代理，把接口调用翻译成 HTTP 请求。

## 第九个问题：单体和微服务

### 一、单体架构 vs 微服务架构

**单体架构（Monolith）**：整个应用打包成一个部署单元，所有模块（用户、订单、库存等）跑在同一个进程里，共用一个数据库。

**微服务架构（Microservices）**：把系统拆成多个独立部署、独立运行的小服务，每个服务负责一块业务（用户服务、订单服务、库存服务），服务之间通过网络（HTTP / RPC / 消息队列）通信，通常每个服务有自己独立的数据库。

| 维度 | 单体 | 微服务 |
| --- | --- | --- |
| 部署 | 一次部署全部上线 | 每个服务独立部署 |
| 扩展性 | 只能整体扩容 | 可以针对某个服务单独扩容 |
| 技术栈 | 通常统一 | 可以每个服务用不同技术栈 |
| 故障影响 | 一个模块挂了可能拖垮整个系统 | 单个服务故障影响范围可控 |
| 复杂度 | 开发简单，但代码库会越来越臃肿 | 需要处理分布式事务、服务发现、链路追踪等额外复杂度 |

**单体架构的优点**：开发和部署简单，适合业务规模较小、团队协作成本相对低的场景。

**微服务架构的优点**：扩展性更强，服务边界更清晰，某个服务出问题时影响范围更可控。

**微服务架构的缺点**：需要处理服务拆分、服务治理、分布式事务、调用链追踪等额外复杂度。

### 二、Spring Boot vs Spring Cloud

**Spring Boot** 解决的是：**怎么快速搭建一个独立的、生产级别的 Java 应用**。

- 自动配置（Auto-Configuration）
- 内嵌 Tomcat，不用单独部署 war 包
- starter 依赖简化配置
- 它是用来构建“单个服务”的框架，不管你是单体还是微服务中的一个服务节点，都可以用 Spring Boot 来写

**Spring Cloud** 解决的是：**当你有了很多个 Spring Boot 服务之后，怎么让它们协同工作**。

- 服务怎么互相发现（服务注册与发现 —— Nacos / Eureka）
- 服务之间怎么调用（声明式 HTTP 客户端 —— OpenFeign）
- 请求量大了怎么分流（负载均衡 —— Spring Cloud LoadBalancer）
- 某个服务挂了怎么办（熔断降级 —— Sentinel / Hystrix）
- 配置文件分散在几十个服务里怎么统一管理（配置中心 —— Nacos Config / Apollo）
- 外部请求怎么统一入口分发到各个服务（网关 —— Spring Cloud Gateway）
- 一个请求跨了多个服务，出问题了怎么排查（链路追踪 —— SkyWalking / Zipkin / Sleuth）

### 三、一句话总结两者关系

> Spring Boot 是用来造“单个服务”的工具，Spring Cloud 是用来把多个服务组织成一个协同工作的分布式系统的工具。

### 四、面试标准回答

> Spring Boot 解决的是单个应用怎么快速搭建、自动配置的问题，本质上不管是单体还是微服务，写具体服务代码时都会用它。Spring Cloud 是在微服务架构下，解决服务间协同问题的一整套解决方案，包括服务注册发现、负载均衡、熔断降级、配置中心、网关、链路追踪这些能力。可以理解为：如果只有一个服务，用 Spring Boot 就够了；一旦拆成多个服务需要互相配合，就需要引入 Spring Cloud 来解决服务治理的问题。

### 五、结合项目的回答方向

如果面试官问到“你的几个平台之间是怎么协调的、有没有用 Spring Cloud 的组件”，可以直接这样回答：

> 这些服务之间如果是独立部署、独立运行，并且通过注册中心、服务发现、HTTP / MQ 进行通信，那么它们就是微服务架构中的服务。Spring Boot 负责每个服务的独立开发与运行，Spring Cloud 则负责这些服务之间的服务治理，例如注册发现、调用、负载均衡、配置管理和链路追踪。这个问题需要提前确认具体是怎么落地的，比如是否用了 Nacos、Feign、Gateway 这类组件。

### 口播版

> Spring Boot 是构建单个服务的框架，Spring Cloud 是把多个服务协同起来的治理框架。简单说，如果只有一个应用，用 Spring Boot 就够了；如果有多个服务需要互相发现、调用和治理，就要引入 Spring Cloud。

## 第十个问题：微服务之间，如何进行通信

微服务之间的通信，通常分为两种：**同步通信** 和 **异步通信**。

### 一、同步通信

同步通信的典型方式是：

- **HTTP / REST**：最常见的方式，适合服务之间的直接调用，常见于订单服务调用用户服务、支付服务调用库存服务。
- **Feign / OpenFeign**：在 Spring Cloud 体系里，通常用 Feign 来封装 HTTP 调用，代码更简洁，调用方式更像本地方法调用。
- **RPC / gRPC**：适合高性能、强类型、内部服务之间的调用，常用于对延迟要求更高的场景。

同步通信的特点是：

- 调用方需要等待响应
- 更适合需要实时返回结果的场景
- 需要考虑超时、重试、熔断、限流等机制

### 二、异步通信

异步通信的典型方式是：

- **消息队列（MQ）**：例如 Kafka、RabbitMQ、RocketMQ 等。
- **事件驱动（Event-Driven）**：服务A发出一个事件，服务B监听事件并处理。

异步通信的特点是：

- 调用方不需要等待对方立即处理完成
- 更适合解耦、削峰、异步处理、扩展吞吐量
- 常见场景包括：订单创建后通知库存扣减、支付成功后发消息给积分服务、日志采集和审计事件处理

### 三、什么时候用哪种方式

- **强一致性、实时查询**：优先用同步调用
- **非实时、可容忍延迟**：优先用异步消息
- **高性能内部服务调用**：可以考虑 gRPC
- **跨服务解耦、流量削峰**：优先用 MQ

### 四、实际项目里常见的做法

在真实项目中，通常不会只用一种通信方式，而是混合使用：

- 用户服务、订单服务之间常用 HTTP / Feign 做同步调用
- 下单成功后，订单服务通过 MQ 通知库存服务、支付服务、通知服务
- 这样既能保持接口调用的实时性，又能提升系统的扩展性和稳定性

### 五、微服务通信的关键注意点

微服务之间通信时，最重要的是要处理好：

- **接口约定**：服务之间的协议、字段、版本要明确
- **幂等性**：消息重复消费或重试时，不能产生脏数据
- **超时和重试**：防止服务雪崩
- **熔断降级**：某个服务不可用时，避免整条链路被拖垮
- **链路追踪**：方便排查跨服务调用的问题
- **数据一致性**：同步调用不能完全替代异步事件，分布式场景下需要权衡一致性和可用性

### 六、面试中可以直接这样回答

> 微服务之间的通信主要分为同步通信和异步通信两种。同步通信常见于 HTTP / REST、Feign、gRPC，适合需要实时响应的场景；异步通信常见于消息队列和事件驱动，适合解耦、削峰和异步处理。实际项目里通常会结合使用：例如订单服务通过 Feign 调用用户服务，订单创建成功后再通过 MQ 发送事件给库存、支付、通知等服务。关键点是要处理好接口约定、超时重试、幂等性、熔断降级和链路追踪。

### 口播版

> 微服务之间的通信主要分同步和异步两种。同步调用常见于 HTTP / Feign / gRPC，适合实时查询；异步通信常见于 MQ 和事件驱动，适合解耦和流量削峰。真实项目里一般会混合使用，比如同步拿实时结果，异步做后续处理。

## 第十二个问题：微服务间调用慢的排查与解决方案

### 一、先说结论

微服务间调用慢，通常分两类：

1. **调用链路上有超时、排队、线程池耗尽、熔断等治理问题**
2. **目标服务本身慢**，比如 SQL 慢、缓存命中率低、内部串行调用过多

所以排查时，通常先看“是不是调用链路自己卡住了”，再看“是不是被调用服务本身慢”。

### 二、治理层面的解决方案

#### 1. 设置合理的超时时间

最基础也最容易被忽略。避免“无限等待”拖垮调用方线程池。

```yaml
# 例如 Feign / OpenFeign
feign:
  client:
    config:
      default:
        connectTimeout: 1000
        readTimeout: 2000
```

#### 2. 熔断降级

当慢服务响应时间过长或失败率过高时，直接走降级逻辑，避免整个调用链被拖垮。

```java
@SentinelResource(value = "callSlowService",
    fallback = "fallbackMethod",
    blockHandler = "blockHandler")
public Result callSlowService() {
    return remoteService.call();
}

public Result fallbackMethod(Throwable t) {
    return Result.defaultValue();
}
```

#### 3. 隔离仓（线程池 / 信号量隔离）

把调用慢服务的线程池单独隔离出来，避免它占满整个应用的线程资源，拖累其他接口。

#### 4. 异步化改造

如果业务允许，把同步调用改成异步：

- **消息队列**：调用方发消息，慢服务异步处理
- **异步非阻塞调用**：用 WebClient / CompletableFuture 代替阻塞式 HTTP 调用

#### 5. 缓存

如果慢服务返回的数据变化不频繁，可以加缓存：

- 本地缓存：Caffeine
- 分布式缓存：Redis
- 也可以采用“缓存 + 定时刷新”的方式，减少实时依赖

#### 6. 限流保护慢服务，同时反向思考

如果慢是因为流量过大导致的，可以：

- 给慢服务本身扩容
- 在调用方限流，避免继续加压

### 三、针对“目标服务本身慢”的优化建议

如果排查发现问题出在被调用方本身，可以从以下几个方向优化：

- **优化慢 SQL**：加索引、避免 N+1 查询
- **减少不必要的远程调用**：避免服务内部串行调用过多
- **增加缓存层**：提升热点数据命中率
- **拆分接口**：把重逻辑做成异步接口，先返回受理成功，再通过回调 / 轮询获取结果

### 四、面试中可以直接这样回答

> 微服务间调用慢，通常先看是不是调用链路出现了超时、线程池耗尽、熔断或限流等治理问题；如果这些治理层面没有问题，再看目标服务本身是不是慢，比如 SQL 慢、缓存不命中、内部串行调用过多。常见解决方案包括设置合理超时时间、熔断降级、线程池隔离、异步化、缓存和限流。目标服务本身慢时，就要从 SQL 优化、减少远程调用、增加缓存和拆分异步接口等方向入手。

### 五、30 秒口播版

> 微服务之间调用慢，第一步要区分是“链路慢”还是“目标服务本身慢”。链路慢一般是超时、线程池耗尽、熔断、限流这些治理问题；目标服务慢通常是 SQL 慢、缓存不命中、内部串行调用过多。常见做法包括设置合理超时时间、熔断降级、线程池隔离、异步化、加缓存和限流。目标服务本身慢的话，就要继续优化 SQL、减少不必要调用、增加缓存，必要时把重逻辑拆成异步接口。

## 第十三个问题：数据库：索引原理、事务隔离级别、锁机制

### 一、索引原理

**底层数据结构：B+ 树**

MySQL InnoDB 使用 B+ 树作为索引结构，原因是：

- 相比二叉树，B+ 树是多叉树，树高更低，减少磁盘 I/O 次数
- 相比 B 树，B+ 树非叶子节点不存数据，只存索引键，可以容纳更多索引项
- 叶子节点之间用双向链表连接，便于范围查询和排序

**聚簇索引 vs 非聚簇索引**

- **聚簇索引（主键索引）**：叶子节点存储的是整行数据。一张表只能有一个聚簇索引
- **二级索引（普通索引）**：叶子节点存储的是主键值，查到主键后需要再回主键索引查一次完整数据，这个过程叫**回表**

**联合索引与最左前缀原则**

```sql
KEY idx_a_b_c (a, b, c)
```

- 索引按 `a` 排序，`a` 相同再按 `b` 排序，以此类推
- 查询必须从最左列开始连续使用才能走索引：`WHERE a=1 AND b=2` 能用索引，`WHERE b=2` 不能
- **索引下推（ICP）**：MySQL 5.6+ 优化，`WHERE a=1 AND c=3`（b 不在条件里），会在索引层面先过滤 `c`，减少回表次数

**覆盖索引**：如果查询的字段全部包含在索引里，不需要回表，直接从索引返回，效率很高。

```sql
-- idx_a_b_c 覆盖了 a,b,c，这个查询不用回表
SELECT a, b, c FROM t WHERE a = 1;
```

**索引失效常见场景**

- 索引列上做函数运算、隐式类型转换
- `LIKE` 以 `%` 开头
- 使用 `!=` 或 `OR`（OR 两边有一边没索引会导致整体失效）
- 数据量小或区分度低，优化器判断走全表扫描更快

### 二、事务隔离级别

**四大特性 ACID**：原子性、一致性、隔离性、持久性

**并发问题**：

- **脏读**：读到了别的事务未提交的数据
- **不可重复读**：同一事务内两次读同一行，结果不一样
- **幻读**：同一事务内两次范围查询，结果集数量不一样

**四种隔离级别**（MySQL 默认 `REPEATABLE READ`）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | ❌ | ❌ | ❌ |
| READ COMMITTED | ✅ | ❌ | ❌ |
| REPEATABLE READ | ✅ | ✅ | ✅（MySQL 下基本解决） |
| SERIALIZABLE | ✅ | ✅ | ✅ |

**MySQL 为什么 RR 级别能基本解决幻读**：

- 快照读（普通 `select`）：靠 **MVCC**，事务开始时生成一个 `ReadView`，之后都读这个快照
- 当前读（`select for update` / `update` / `delete`）：靠 **Next-Key Lock（间隙锁 + 行锁）**，锁住范围，阻止其他事务插入

**MVCC 核心概念**：

- 每行数据有隐藏字段：事务 ID（`trx_id`）、回滚指针（`roll_pointer`）
- 通过 undo log 构建历史版本链
- `ReadView` 判断某个版本对当前事务是否可见

### 三、锁机制

**按粒度分**：

- **表锁**：开销小，加锁快，但并发度低
- **行锁**：开销大，加锁慢，但并发度高（InnoDB 默认，只有走索引才会用行锁，否则退化为表锁）

**按类型分**：

- **共享锁（S 锁）**：读锁，多个事务可同时持有
- **排他锁（X 锁）**：写锁，同一时间只能一个事务持有

**InnoDB 特有锁**：

- **Record Lock**：锁单条记录
- **Gap Lock（间隙锁）**：锁记录之间的空隙，防止插入
- **Next-Key Lock**：Record Lock + Gap Lock 的组合，锁定一个左开右闭区间

**意向锁**：为了让表锁和行锁能够共存判断冲突，加行锁前会先在表上加一个意向锁（IS / IX）。

**死锁**：

- 产生条件：两个事务互相持有对方需要的锁，形成循环等待
- InnoDB 有死锁检测机制，自动回滚一个事务打破死锁
- 避免死锁：按固定顺序访问表和行、事务尽量短、给查询加合适索引减少锁范围

### 口播版

> 数据库这块我会重点说三点：索引靠 B+ 树实现，联合索引要遵守最左前缀原则；事务隔离级别里，MySQL 默认 RR 能基本解决幻读，靠 MVCC 和 Next-Key Lock；锁机制里，InnoDB 的行锁和间隙锁是核心，死锁要靠索引和固定访问顺序来避免。

## 第十四个问题：缓存：一致性问题、雪崩穿透击穿

### 一、缓存一致性问题（数据库 + Redis）

核心矛盾：**双写操作无法保证原子性**，更新数据库和更新缓存之间总有间隙。

**常见方案对比**：

- **先更新缓存，再更新数据库**：不推荐；数据库失败会导致缓存和库不一致
- **先更新数据库，再更新缓存**：并发下容易出现旧值覆盖新值
- **先删缓存，再更新数据库**：读请求可能在更新前读到旧数据，再写回缓存
- **先更新数据库，再删缓存（Cache Aside，业界主流）**：最常见，极端情况下仍有小概率不一致

**Cache Aside 模式的极端不一致场景**：

1. 读请求缓存未命中，准备查数据库
2. 写请求更新数据库并删除缓存
3. 读请求把旧数据写回缓存

这种情况概率极低，通常接受。

**延迟双删**：

```text
1. 删除缓存
2. 更新数据库
3. sleep 一段时间
4. 再删一次缓存
```

**终极方案：读取 binlog 异步更新缓存**

用 Canal 监听 MySQL binlog，数据库变更后异步删除或更新缓存，实现最终一致。

### 二、缓存雪崩、穿透、击穿

| 问题 | 原因 | 解决方案 |
| --- | --- | --- |
| 穿透 | 查询缓存和数据库都不存在的数据，导致每次打到数据库 | 缓存空值、布隆过滤器、参数校验 |
| 击穿 | 单个热点 key 过期，大量并发请求同时打到数据库 | 热点 key 不设过期、逻辑过期、分布式锁、提前预热 |
| 雪崩 | 大量 key 同时过期，或 Redis 整体挂掉 | 随机过期时间、缓存高可用、熔断降级、限流 |

**分布式锁解决击穿的典型写法**：

```java
public Object getData(String key) {
    Object value = redis.get(key);
    if (value == null) {
        if (redis.setnx(lockKey, "1", 10)) {
            try {
                value = db.query(key);
                redis.set(key, value, expireTime);
            } finally {
                redis.del(lockKey);
            }
        } else {
            Thread.sleep(50);
            return getData(key);
        }
    }
    return value;
}
```

### 口播版

> 缓存一致性这里要重点抓住两点：一是数据库和缓存的更新顺序很难保证原子性，二是业界主流是 Cache Aside 模式。雪崩、穿透、击穿这三种问题的核心区别是：穿透是“查不到的数据频繁打库”，击穿是“热点 key 过期后大量请求打库”，雪崩是“很多 key 一起失效或 Redis 整体失效”。

## 第十五个问题：消息队列：如何保证消息不丢失、顺序消费

### 一、如何保证消息不丢失

消息丢失分三段：生产者 → MQ、MQ 自身、MQ → 消费者。

**① 生产者 → MQ**

- 使用**同步发送 + ACK 确认机制**
- 发送失败设置重试机制
- 极端情况可以先落本地消息表，定时补偿发送

**② MQ 自身**

- 开启持久化：RabbitMQ 队列和消息都持久化；Kafka 设置 `replication.factor >= 2`，并要求 `acks=all`
- 集群部署，避免单点故障

**③ MQ → 消费者**

- 使用**手动 ACK**，业务处理完成后再确认
- 消费失败要有重试和死信队列兜底，不能直接丢弃

```java
@RabbitListener(queues = "order.queue")
public void handle(Message message, Channel channel) throws IOException {
    try {
        process(message);
        channel.basicAck(message.getDeliveryTag(), false);
    } catch (Exception e) {
        channel.basicNack(message.getDeliveryTag(), false, true);
    }
}
```

### 二、顺序消费

**关键前提：全局顺序很难保证，通常只保证局部（分区/队列级）有序。**

**RocketMQ 方案**：

- 同一业务 key 的消息发到同一个 queue
- 让一个 queue 只被一个消费者线程消费

**Kafka 方案**：

- 同一个 key 的消息通过 hash 路由到同一个 partition
- 一个 partition 只能被同一消费组内的一个消费者消费

**注意点**：

- 顺序消费会牺牲并发度
- 如果消费失败重试，要注意不能让后面的消息插队执行，否则乱序依然会出现

### 口播版

> 消息不丢失的关键是三点：生产者要有确认与重试，MQ 自身要持久化和集群化，消费者要手动 ACK 并有重试和死信兜底。顺序消费的核心是让同一业务 key 的消息落到同一个队列或 partition，然后只让一个线程消费，这样才能保证局部有序。

## 第十六个问题：JVM：垃圾回收、内存模型

### 一、垃圾回收

**判断对象是否存活**

- 引用计数法：有循环引用问题，因此 Java 不采用
- **可达性分析算法**：从 GC Roots 出发，不可达的对象才是垃圾

**分代回收思想**：对象分为新生代和老年代。

- 新生代：对象朝生夕死，用 **复制算法**（Minor GC / Young GC）
- 老年代：对象存活率高，用 **标记-清除** 或 **标记-整理算法**（Major GC / Full GC）

**对象晋升老年代的条件**：

- 经历一定次数 Minor GC 后还存活
- 大对象直接进老年代
- 动态年龄判断：Survivor 区中同年龄对象总和超过一半，则大于等于该年龄的对象直接进老年代

**常见垃圾回收器**：

- Serial：单线程，适合客户端应用
- Parallel Scavenge：多线程，注重吞吐量
- CMS：并发标记清除，已废弃
- G1：可预测停顿时间，JDK9+ 默认
- ZGC / Shenandoah：超大堆、低延迟场景

**CMS vs G1**：

- CMS 是“标记-清除”，容易产生碎片
- G1 是“标记-整理+分区回收”，能更好控制停顿时间

### 二、Java 内存模型（JMM）

**运行时数据区**：

- **线程共享**：堆、方法区 / 元空间
- **线程私有**：虚拟机栈、本地方法栈、程序计数器

**JMM 三大特性**：

- **原子性**：一个操作不可被中断
- **可见性**：一个线程修改了变量，其他线程能立即看到
- **有序性**：程序执行顺序按代码顺序执行

**volatile 原理**：

- 修改后立即刷新到主内存，并使其他线程工作内存中的副本失效
- 通过插入内存屏障禁止指令重排序
- 它能保证可见性和有序性，但不能保证复合操作原子性

**happens-before 原则**：

- 程序次序规则
- 锁规则
- volatile 规则
- 线程启动规则

### 口播版

> JVM 这块我会重点说两点：一是 GC 的核心是分代回收，年轻代用复制算法，老年代用标记整理或清除；二是 JMM 讲的是并发下内存可见性、原子性和有序性，volatile 关键点就是保证可见性和禁止重排，但不能替代锁。

## 第十七个问题：Spring：IOC / AOP 原理、Bean 生命周期

### 一、IOC 原理

**核心思想**：把对象的创建和依赖关系的管理，从代码里剥离出来交给 Spring 容器。

**大致流程**：

1. 读取配置（XML / 注解 / JavaConfig），解析成 `BeanDefinition`
2. 通过 `BeanFactory` / `ApplicationContext` 根据 `BeanDefinition` 创建 Bean
3. 处理依赖注入（构造器注入、setter 注入、字段注入）
4. 放入单例池（`singletonObjects`）供后续获取

**常见注入方式对比**：

- 构造器注入更推荐，因为依赖更明确、可变更少、容易单测

### 二、AOP 原理

**核心思想**：把横切关注点从业务逻辑中抽离，动态织入增强功能。

**底层实现：动态代理**

- **JDK 动态代理**：目标类实现接口时使用
- **CGLIB 动态代理**：目标类没有实现接口时使用，基于继承生成子类
- Spring Boot 2.x 后默认使用 CGLIB（除非明确配置）

**核心概念**：

- 切面（Aspect）
- 切点（Pointcut）
- 通知（Advice）

`@Transactional` 本质上就是一个典型的 AOP 应用：方法执行前开启事务，成功提交，异常回滚。

**AOP 常见失效场景**：

- 同一个类内部方法互相调用
- 方法不是 `public`
- 目标类没有被 Spring 管理

### 三、Bean 生命周期

完整流程：

1. 实例化（Instantiation）
2. 属性赋值（Populate）
3. Aware 接口回调
4. BeanPostProcessor 前置处理
5. 初始化：`@PostConstruct`、`InitializingBean.afterPropertiesSet()`、`init-method`
6. BeanPostProcessor 后置处理（AOP 代理就是在这里生成的）
7. Bean 可以被使用
8. 容器关闭时，执行销毁回调：`@PreDestroy`、`DisposableBean.destroy()`、`destroy-method`

**关键点**：AOP 代理对象是在 `BeanPostProcessor` 的 `postProcessAfterInitialization` 阶段生成的。

**循环依赖问题**：Spring 通过三级缓存解决单例 Bean 的循环依赖：

- 一级缓存：完整成品 Bean
- 二级缓存：早期暴露 Bean
- 三级缓存：`ObjectFactory`，用于生成代理对象

构造器注入的循环依赖 Spring 无法解决，会直接抛 `BeanCurrentlyInCreationException`。

### 口播版

> Spring 这块我会按三层说：IOC 负责对象创建和依赖注入，AOP 负责把日志、事务这样的横切逻辑从业务代码里抽离，Bean 生命周期则是从实例化、属性赋值、初始化到销毁的完整过程。面试里最容易追问的是 AOP 为什么失效以及循环依赖如何解决。

## 第十八个问题：一般情况下如何对接口做幂等

### 一、什么是幂等

幂等是指：同一个请求重复执行多次，结果和执行一次相同，不会产生额外副作用。

常见场景包括：

- 支付、退款、下单、发券等涉及金钱或订单状态的操作
- 网络重试、用户重复点击、消息重复投递
- 服务调用超时后客户端重复发起请求

### 二、幂等的常见实现方案

#### 方案一：客户端生成唯一业务 ID

客户端在请求时携带一个全局唯一的业务 ID（例如 `requestId`、`orderId`、`paymentId`），服务端拿到后先判断这个 ID 是否已处理过。

```text
POST /pay
{
  "requestId": "a9e5d9f0-8ec0-4f4d-9bb9-93c1d6d50f61",
  "orderId": "1001",
  "amount": 100
}
```

服务端可以用：

- 去重表：`request_id` 唯一索引
- Redis `SETNX`：先判断是否已经处理
- 业务状态机：如果状态已为已支付，就直接返回成功

#### 方案二：数据库唯一索引 + 事务

这是最稳妥、最常用的方式之一。把“业务唯一键”设计成唯一索引，再在事务里执行真正的处理逻辑。

例如：

```sql
CREATE TABLE payment_request (
    request_id VARCHAR(64) PRIMARY KEY,
    order_id BIGINT NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

请求处理时：

```sql
BEGIN;

INSERT INTO payment_request(request_id, order_id, status)
VALUES ('a9e5d9f0-8ec0-4f4d-9bb9-93c1d6d50f61', 1001, 1);

-- 真正的支付逻辑
UPDATE orders SET status = 'PAID' WHERE id = 1001 AND status != 'PAID';

COMMIT;
```

如果重复请求到来，插入相同的 `request_id` 会失败，事务回滚，重复请求不会重复处理。

#### 方案三：状态机 + CAS

适合订单状态、支付状态、审批状态这类有限状态流转。

例如：

```text
未支付 -> 已支付 -> 已退款
```

业务逻辑可以写成：

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 1001
  AND status = 'UNPAID';
```

如果重复执行这条 SQL，第二次更新因为条件不满足，`affected rows = 0`，自然达到幂等效果。

#### 方案四：分布式锁 / 业务锁

在高并发场景下，可以在处理关键逻辑前加锁，确保同一时刻只有一个线程在执行。

```java
synchronized(lock) {
    // 执行关键逻辑
}
```

或者用 Redis 分布式锁：

```java
Boolean locked = redisTemplate.opsForValue().setIfAbsent(key, value, 30, TimeUnit.SECONDS);
if (locked) {
    try {
        // 处理业务
    } finally {
        redisTemplate.delete(key);
    }
}
```

这种方案适合处理非常短的临界区，但要注意锁超时、锁释放失败、死锁等问题。

### 三、幂等方案怎么选

如果是强一致性的业务，比如支付、退款、订单状态更新，通常推荐：

1. 客户端带唯一业务 ID
2. 服务端用幂等表或唯一索引去重
3. 业务逻辑用状态机控制状态流转
4. 事务中完成状态更新

这样既能保证结果正确，也能避免重复扣款、重复发券、重复状态变更。

### 四、注意点

- 幂等键要能唯一标识“一次业务意图”，通常由**客户端生成**，这样网络重试时才能带着同一个 key
- 需要考虑**幂等记录的过期时间**，避免表无限增长
- 分布式场景下要注意锁和数据库操作的**原子性**，防止竞态条件
- 返回结果要一致：重复请求应返回与首次相同的响应内容和状态码

### 口播版

> 接口幂等的核心就是让同一个业务意图无论重复提交多少次，最终都只产生一次效果。最常见的方法是唯一业务 ID 加去重表，或者用数据库唯一索引和状态机来保证；如果是支付、下单这种强一致性场景，我会优先用幂等表加唯一索引，再结合事务保证。

## 第十九个问题：乐观锁 vs 悲观锁

两者都是解决并发场景下数据一致性问题的锁机制，核心区别在于**对"冲突发生概率"的假设不同**。

### 一、核心思想

乐观锁

### 二、悲观锁

**思路**：拿到数据前先加锁，这期间其他事务都不能读/写（视锁类型而定），操作完释放锁。

#### 实现方式

```
-- MySQL InnoDB：SELECT ... FOR UPDATE
BEGIN;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;  -- 加排他锁
UPDATE orders SET status = 'PAID' WHERE id = 1;
COMMIT;
```

其他事务此时执行同样的 `FOR UPDATE` 会被阻塞，直到锁释放。

也可以用**分布式锁**（Redis、ZooKeeper）实现跨服务的悲观锁。

#### 特点

- ✅ 强一致性，绝对安全
- ❌ 并发性能差（阻塞等待）
- ❌ 有死锁风险
- ❌ 持锁时间长会拖垮吞吐量

#### 适用场景

- 写冲突概率高（如秒杀扣库存的最后一步）
- 对一致性要求极高，宁可牺牲性能

### 三、乐观锁

**思路**：不加锁，假设大概率不会冲突。更新时通过**版本号**或**时间戳**判断这段时间内数据是否被别人改过，如果改过就更新失败，重试或报错。

#### 实现方式一：版本号（version）

```
-- 读取时拿到 version
SELECT id, stock, version FROM product WHERE id = 1;
-- 假设查到 version = 5

-- 更新时带上version作为条件
UPDATE product 
SET stock = stock - 1, version = version + 1 
WHERE id = 1 AND version = 5;
```

如果 `affected rows = 0`，说明期间有别人抢先修改了，本次更新失败，可以重试。

#### 实现方式二：CAS（比较后再更新，无需额外字段）

```
UPDATE product SET stock = stock - 1 
WHERE id = 1 AND stock > 0;
```

#### 特点

- ✅ 不阻塞，并发性能好
- ✅ 无死锁风险
- ❌ 冲突多时失败率高，需要**重试机制**（自旋/重试次数上限）
- ❌ 只能保护单条记录/单次更新，逻辑较复杂的场景需要额外设计

#### 适用场景

- 读多写少
- 冲突概率低（比如用户修改自己的资料）
- 高并发、对吞吐量要求高的场景

### 五、和幂等的关系

回到你之前问的幂等问题：

- 悲观锁常用于**方案四**（加锁执行关键逻辑，防止并发重复处理）
- 乐观锁常用于**方案三**（状态机 + CAS，比如订单状态从"未支付"→"已支付"只允许成功一次，天然实现了幂等）

一般建议：**优先用乐观锁**（性能好），只有在冲突特别频繁、乐观锁重试代价太高时，才考虑悲观锁。

## 第二十二个问题：SpringBoot 自动装配启动流程

### 一、入口：`@SpringBootApplication`

启动类上的 `@SpringBootApplication` 是一个复合注解，核心由三部分组成：

```java
@SpringBootConfiguration   // 本质是 @Configuration
@EnableAutoConfiguration   // 开启自动配置的核心注解
@ComponentScan             // 组件扫描
```

真正触发自动装配的是 `@EnableAutoConfiguration`。

### 二、`@EnableAutoConfiguration` 做了什么

这个注解上标注了：

```java
@Import(AutoConfigurationImportSelector.class)
```

`@Import` 会把 `AutoConfigurationImportSelector` 这个类导入到 Spring 容器的处理流程中，它实现了 `DeferredImportSelector` 接口（延迟导入选择器），会在所有 `@Configuration` 类处理完后再执行。

### 三、`AutoConfigurationImportSelector` 的核心流程

它的 `process()` / `selectImports()` 方法大致做以下几件事：

1. **判断是否启用自动配置**（检查 `spring.boot.enableautoconfiguration` 属性，默认 true）
2. **获取候选配置类列表**：通过 `SpringFactoriesLoader` 读取
   - Spring Boot 2.x：`META-INF/spring.factories` 中 `EnableAutoConfiguration` 对应的类名列表
   - Spring Boot 2.7+/3.x：改为读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件（纯文本，一行一个类名，性能更好）
3. **去重、排除**（处理 `exclude` / `excludeName` 属性排除的类）
4. **应用过滤器（AutoConfigurationImportFilter）**，其中最关键的是 `OnClassCondition`，提前根据 `@ConditionalOnClass` 过滤掉 classpath 中不存在依赖的配置类，减少后续加载开销
5. 返回最终需要导入的自动配置类全限定名数组

### 四、条件装配生效阶段

被选中的自动配置类（如 `DataSourceAutoConfiguration`、`WebMvcAutoConfiguration`）会作为普通 `@Configuration` 类被加载，此时容器会逐一解析类和方法上的条件注解：

- `@ConditionalOnClass` / `@ConditionalOnMissingClass`：classpath 是否存在某类
- `@ConditionalOnBean` / `@ConditionalOnMissingBean`：容器中是否已有/没有某 Bean（常用于让用户自定义配置覆盖默认配置）
- `@ConditionalOnProperty`：配置文件中某属性是否满足条件
- `@ConditionalOnWebApplication`：是否是 Web 应用
- `@ConditionalOnResource`、`@ConditionalOnExpression` 等

只有条件全部满足的配置类/方法才会真正生效，把对应的 Bean 注册进容器。

### 五、整体时序图

```text
main()
 → SpringApplication.run()
   → 准备 Environment
   → 创建 ApplicationContext
   → refresh()
     → invokeBeanFactoryPostProcessors
       → ConfigurationClassPostProcessor 处理 @Configuration
         → 解析 @ComponentScan、@Import
           → 触发 AutoConfigurationImportSelector(DeferredImportSelector)
             → 读取 imports 文件/spring.factories
             → OnClassCondition 等过滤器预过滤
             → 生成最终自动配置类列表
     → 逐个解析自动配置类上的 @Conditional 注解
       → 条件满足的类中的 @Bean 方法注册到容器
```

### 六、关键点总结

| 环节 | 作用 |
| --- | --- |
| `@Import(AutoConfigurationImportSelector.class)` | 装配入口 |
| `DeferredImportSelector` | 保证在用户自定义配置之后处理，便于“覆盖默认” |
| `spring.factories` / `*.imports` 文件 | 声明“有哪些候选自动配置类”（SPI 机制） |
| `@ConditionalOnXxx` 系列注解 | 决定某个配置“是否真正生效” |
| `spring-boot-autoconfigure` 依赖 | 提供了绝大多数官方自动配置类 |

一句话概括：**SpringBoot 通过 SPI 机制批量加载候选自动配置类，再用一整套 `@Conditional` 条件注解按需筛选生效，实现“约定优于配置”的自动装配。**

### 口播版

> SpringBoot 的自动装配，本质上是从 `@SpringBootApplication` 入手，先通过 `@EnableAutoConfiguration` 触发自动配置入口，然后由 `AutoConfigurationImportSelector` 读取候选配置类列表，再经过 `@ConditionalOnXxx` 系列条件判断，只有满足条件的配置才会真正注册到容器里。重点记住一点：它是用 SPI 机制先拿到候选配置，再按条件筛选生效，最终实现“开箱即用”的自动装配。

## 第二十三个问题：SQL 连接类型详解（附集合类比）

### 一、先建立集合类比的直觉

假设有两个集合（表）：

- **A 表**（左表）：`{1, 2, 3}`
- **B 表**（右表）：`{2, 3, 4}`

把“能匹配上”的部分想象成两个圆的交集，SQL 连接本质上就是在操作这两个“圆”。

```text
     A表           B表
   ┌───────┐   ┌───────┐
   │ 1  2  │ 3 │ 2  4  │
   │       │   │       │
   └───────┘   └───────┘
        └── 交集: 2,3 ──┘
```

### 二、内连接（INNER JOIN）= 交集 ∩

**只保留两边都能匹配上的数据**，类比集合的 **交集**。

```sql
SELECT * FROM A INNER JOIN B ON A.id = B.id;
```

结果：只有 `{2, 3}`（A、B 里都有的部分）

```text
A: 1  [2] [3]
B:    [2] [3]  4
结果 = {2, 3}
```

### 三、左连接（LEFT JOIN）= 保留左边全集

**左表全部保留，右表匹配不上的补 NULL**，类比集合中 **“以左边为基准，右边能配则配，不能配也不丢左边的数据”**。

```sql
SELECT * FROM A LEFT JOIN B ON A.id = B.id;
```

结果：`{1, 2, 3}` 全部保留，其中 1 对应的 B 字段是 NULL

```text
A: [1]  [2]  [3]
B:  NULL [2]  [3]
结果 = {1(B为空), 2, 3}
```

**集合表达式：A（全部） + (A∩B) 对应的 B 值**，可以理解为 **A ∪ (A∩B)**，但 A 本身已经包含交集了，所以更准确说是：**以 A 为主体，不删减任何 A 的行**。

### 四、右连接（RIGHT JOIN）= 保留右边全集

和左连接完全对称，**右表全部保留，左表匹配不上的补 NULL**。

```sql
SELECT * FROM A RIGHT JOIN B ON A.id = B.id;
```

结果：`{2, 3, 4}` 全部保留，4 对应的 A 字段是 NULL

```text
A: 1  [2] [3]  NULL
B:    [2] [3]  [4]
结果 = {2, 3, 4(A为空)}
```

> 💡 小技巧：`A RIGHT JOIN B` 等价于 `B LEFT JOIN A`，只是写法习惯不同，实际项目里很多规范会**只用 LEFT JOIN、不用 RIGHT JOIN**，把表顺序换一下即可，减少理解成本。

### 五、外连接（FULL OUTER JOIN）= 并集 ∪

**两边全部保留，谁匹配不上谁补 NULL**，类比集合的 **并集**。

```sql
SELECT * FROM A FULL OUTER JOIN B ON A.id = B.id;
```

结果：`{1, 2, 3, 4}` 全部出现

```text
A: [1] [2] [3]  NULL
B:  NULL [2] [3]  [4]
结果 = {1(B空), 2, 3, 4(A空)} = A ∪ B
```

> ⚠️ 注意：**MySQL 不支持 `FULL OUTER JOIN` 语法**，需要用 `LEFT JOIN UNION RIGHT JOIN` 模拟：

```sql
SELECT * FROM A LEFT JOIN B ON A.id = B.id
UNION
SELECT * FROM A RIGHT JOIN B ON A.id = B.id;
```

### 六、汇总对比表

| 连接类型 | 集合类比 | 结果集 | 保留方 |
| --- | --- | --- | --- |
| INNER JOIN | 交集 A∩B | `{2, 3}` | 两边都要匹配上 |
| LEFT JOIN | 左表全集 | `{1, 2, 3}` | 左表全保留 |
| RIGHT JOIN | 右表全集 | `{2, 3, 4}` | 右表全保留 |
| FULL OUTER JOIN | 并集 A∪B | `{1, 2, 3, 4}` | 两边全保留 |

### 七、进阶：如何只取“差集”（某一边独有的数据）

面试常考：**只要 A 中有、B 中没有的数据（A - B）**，不能直接用 INNER JOIN，要用 LEFT JOIN + 过滤 NULL：

```sql
SELECT * FROM A LEFT JOIN B ON A.id = B.id
WHERE B.id IS NULL;
```

```text
A: [1] 2  3       ← 只留 B 匹配不上的那部分
结果 = {1}   (对应集合里的 A - B，即 A 的差集)
```

同理，**B 独有的数据（B - A）**：

```sql
SELECT * FROM A RIGHT JOIN B ON A.id = B.id
WHERE A.id IS NULL;
```

结果：`{4}`

**两边都独有的数据（对称差，A△B）**，即“只在一边出现”的部分，MySQL 里这样写：

```sql
SELECT * FROM A LEFT JOIN B ON A.id = B.id WHERE B.id IS NULL
UNION
SELECT * FROM A RIGHT JOIN B ON A.id = B.id WHERE A.id IS NULL;
```

结果：`{1, 4}`，正好对应集合里的 **对称差集**。

### 八、一张图总结所有情况

```text
INNER JOIN:      A∩B         → 图中重叠部分
LEFT JOIN:       A(全)       → 左圆整体 + 交集部分的 B 值
RIGHT JOIN:      B(全)       → 右圆整体 + 交集部分的 A 值
FULL OUTER JOIN: A∪B         → 两个圆整体
LEFT - 交集:     A-B(差集)  → 左圆去掉重叠部分
RIGHT - 交集:    B-A(差集)  → 右圆去掉重叠部分
对称差集:        A△B         → 两圆都去掉重叠部分，只留两端
```

### 口播版

> SQL 连接本质上就是在做集合运算。INNER JOIN 是交集，LEFT JOIN 是保留左表全部数据，RIGHT JOIN 是保留右表全部数据，FULL OUTER JOIN 是并集。面试里最容易被追问的，是怎么用 LEFT JOIN + IS NULL 来拿差集，或者怎么用 UNION 模拟 FULL OUTER JOIN。只要记住“左右表保留哪些行”，这几个连接就很容易区分。

## 第二十四个问题：Java 中 final 关键字的作用

`final` 的核心含义就是：**让某个东西不能再被修改、不能再被重写、不能再被继承**。在面试里可以统一这样回答：

### 一、修饰变量：不能二次赋值

```java
final int age = 18;
// age = 20; // 编译错误
```

- `final` 修饰基本类型变量时，值不能再变化
- `final` 修饰引用类型变量时，引用地址不能再变，但对象内部属性仍然可以被修改

```java
final User user = new User();
user.setName("Tom"); // 允许
// user = new User(); // 不允许
```

### 二、修饰方法：不能被子类重写

```java
class Parent {
    public final void test() {
        System.out.println("父类方法");
    }
}

class Child extends Parent {
    // 编译错误：不能重写 final 方法
    // public void test() {}
}
```

适合用于限制子类行为，防止覆盖关键逻辑。

### 三、修饰类：不能被继承

```java
public final class UserService {
}
```

```java
class MyService extends UserService {
}
```

上面会直接编译失败。`String`、`Integer`、`Long` 等常见类都是 `final` 类。

### 四、修饰成员变量：通常用于常量

```java
public class Config {
    public static final String APP_NAME = "Ana";
    public static final int MAX_SIZE = 100;
}
```

这里的 `static final` 常用于定义类级常量，命名通常用大写字母和下划线。

### 五、统一总结

| 修饰对象 | 作用 |
| --- | --- |
| 变量 | 不能再次赋值 |
| 方法 | 不能被子类重写 |
| 类 | 不能被继承 |
| `static final` 变量 | 常用于定义类级常量 |

### 口播版

> `final` 的核心作用就是限制“再修改”。如果修饰变量，就是不能再次赋值；如果修饰方法，就是不能被子类重写；如果修饰类，就是不能被继承；如果是 `static final`，通常就是定义常量。简单记忆就是：`final` 让某个东西在语义上变成“最终状态”。
